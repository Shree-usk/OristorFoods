# STORY-021: Blog

**Status:** Done
**Epic:** 04 — Recipes & Food Academy
**Priority:** Medium
**Persona(s):** Home Cook, Sri Lankan Expat, Gourmet Food Enthusiast

## User Story
As a Gourmet Food Enthusiast, I want to browse blog posts by tag and author, so that I can follow the topics and voices I'm most interested in.
As a Home Cook, I want to read a blog post and leave a comment, so that I can engage with the brand and other readers.
As a Sri Lankan Expat, I want to page through older blog posts, so that I can catch up on brand stories and content I missed.

## Description
This story builds the customer-facing Blog named in `docs/blueprint.md` Section 4 (primary nav "Blog") and Section 5 ("Content: ...blog..."). It covers the blog listing page (filterable by tag and author, paginated) and the blog post detail page, including a public comment submission and display experience. Comment *moderation* (approve/reject/reply/feature/hide, per Section 7's "Blog — rich text editor, scheduling, authors, tags, comment moderation") is an Admin epic concern and is referenced here only as a dependency/data contract, not implemented in this story.

- [x] Blog post detail page includes a public comment section: a comment submission form (name/email or authenticated customer, comment body) and a list of previously approved comments — `CommentSection` (`comment-section.tsx`) composes `BlogCommentForm` + `BlogCommentList`. **Follow-up fix (final review pass):** an earlier version of this note flagged a real UX friction bug — the form used to always render Name/Email inputs regardless of session state, and since `blogCommentInputSchema`'s `name`/`email` fields are `.optional()` (permits `undefined`, not empty string), an untouched RHF-registered input's `""` failed client-side validation, forcing a signed-in user to type placeholder text into fields the server would ignore anyway. This is now fixed: `BlogCommentForm` calls `useSession()` (same pattern as `ask-question-form.tsx`) and does not render or register Name/Email at all for an authenticated caller, validating against `blogCommentInputSchema` as-is; a guest still sees Name/Email and is validated against the new, genuinely-required `blogGuestCommentInputSchema`. The server independently enforces the same guest requirement (`POST /api/blog/[slug]/comments` re-validates against `blogGuestCommentInputSchema` once it knows there is no session) and the form now surfaces the real HTTP response (success/field errors/root error) instead of always showing the awaiting-approval message — see `tests/unit/blog-comment-form.test.tsx`, `tests/unit/blog-route.test.ts`, and `tests/unit/blog-schema.test.ts`.
- [x] Submitted comments are created with a `PENDING` status and are **not** shown publicly until an admin approves them via the moderation console (STORY-044/045 in Epic 07) — the submitter sees a "your comment is awaiting approval" confirmation state — `createBlogComment` hardcodes `status: "Pending"` at the type level (`blog.repository.ts:136-141`, its input type excludes `status`); `blogPostDetailSelect`'s `comments` relation hardcodes `where: { status: "Approved" }` (`blog.repository.ts:59`); `BlogCommentForm` shows "Thanks — your comment is awaiting approval." on success (`blog-comment-form.tsx:34`). `tests/e2e/blog.spec.ts` ("submitting a comment shows the awaiting-approval message, and the just-submitted comment does not appear after reload") covers the full round trip.
- [x] Comment submission is rate-limited/spam-guarded at minimum with honeypot or equivalent basic protection (full spam/abuse tooling is not required here) — **delivered as worded, with a mechanism note.** A honeypot field (`blogCommentInputSchema.honeypot`) silently no-ops the submission in `submitComment` (`blog.service.ts:156-158`) without a distinguishable response — see the architecture-decisions.md entry on the real bug found and fixed here (commit `48c7601`: the schema itself was rejecting a filled honeypot with a 400, defeating the silent-rejection property, until this story's own review caught it). Rate-limiting is a DB check (`findRecentCommentByIdentity`) scoped to the same post + same identity (`authorEmail` for guests, `customerId` for authenticated customers) within a 60-second window — **not IP-based**, despite the task list's "simple rate limit by IP/session" wording. The AC's own text sets the bar at "honeypot or equivalent basic protection... full spam/abuse tooling is not required" — an identity-scoped DB check clears that bar, so this is checked off, but flagged here explicitly rather than silently treated as equivalent to what the task list originally described.
- [x] Blog pages include SEO meta tags and `Article`/`BlogPosting` structured data — hub has static `metadata` (`page.tsx:12-16`, title/description/canonical) plus `ItemListJsonLd`; detail page has `generateMetadata` (`[slug]/page.tsx:20-29`) and `BlogJsonLd` emitting `"@type": "BlogPosting"` (`blog-json-ld.tsx:14`) — `tests/unit/blog-json-ld.test.tsx` covers the emitted shape.
- [x] Listing and detail pages are fully responsive and meet WCAG 2.1 AA (accessible comment form labels/errors, readable tag/author filter controls) — responsive grid breakpoints (`sm:`/`xl:` grid-cols) on both pages; `tests/e2e/blog.spec.ts` axe scans report zero violations on the hub and on two distinct detail pages (one with resolvable recipe/video embeds, one with an unresolvable embed) — both detail scans include the live comment form, and the hub scan includes the tag/author filter chip navs; `BlogCommentForm` wires `aria-describedby` to each field's error message (`blog-comment-form.tsx:41,50,62`).
